# FinSight 研究链路优化清单

## Summary

### 在新分支：feat/research_chain_redesign上进行开发

目标是优化 FinSight 的完整研究链路：`研究任务配置 → 证券识别 → Agent Run → 实时状态 → 报告发布 → 报告导出 → 基于报告继续研究 → 后续追问`。界面参考 FinRobot 的 Research Launcher、Mission Control，以及 Factor Lab 的任务类型、问题建议、任务队列和历史报告设计，但继续使用 FinSight 已有的 Durable Turn、Checkpoint、Lease、Agent Event Outbox、SSE 和质量门禁，不照搬外部项目的技术栈、积分系统或产品表述。

第一阶段先完成“一次任务、一份报告”的产品化改造；第二阶段增加“基于当前报告继续研究”，仍创建新的独立 Agent Run；第三阶段再建立持久 Research Session 和会话内受限多轮研究。每个研究问题始终拥有独立 AgentState、预算、Checkpoint 和 Tool Journal，不把多轮消息、上一次运行状态和金融事实混在一起。

## Factor Lab 对标结论与取舍

公开页面和官方文档显示，Factor Lab 当前的核心形态是“单轮研究任务 + 异步生成 + 独立报告”，没有发现真正共享上下文的用户多轮对话：

```text
选择证券
  → 选择报告类型
  → 填写一次补充问题
  → 提交异步任务
  → 生成独立报告
  → 在历史记录中阅读、分享或下载
```

概念边界：

- “补充问题”属于第一次任务提交参数，不是第二轮对话。
- “历史 AI 解读”保存多份独立报告，不等于共享上下文的 Conversation Thread。
- “圆桌报告”即使内部存在多个研究角色，也属于多角色生成，不等于用户与 Agent 多轮交互。
- “从报告正文继续发起研究”更适合作为 FinSight 的第二阶段：携带受控报告上下文创建新 Run，而不是直接复用旧 AgentState。

Factor Lab 最值得借鉴的是研究任务产品化，而不是照搬“圆桌”“量价决策”或完整聊天界面。对标依据：[项目介绍](https://github.com/mykernel/factor-lab)、[快速上手](https://github.com/mykernel/factor-lab/blob/main/docs/quickstart.md)、[更新日志](https://github.com/mykernel/factor-lab/blob/main/docs/changelog.md)。

借鉴边界：

- “圆桌报告”暂不作为 P0。多角色讨论只有在能证明增加证据覆盖或结论质量时再引入。
- “量价会诊”若后续实现，统一改为“量价观察”，不输出买卖点、仓位或收益承诺。
- “热门股票”统一改为“示例标的”，不能形成荐股暗示。
- 不复制积分系统；改为展示真实研究深度、实际耗时、模型、Token 和工具调用数据。
- 报告公开分享属于 P2/P3，必须先完成访问控制、脱敏和合规边界。

## Step 1：明确产品链路和字段语义

将新入口的权威链路固定为：

```text
配置研究任务
  → 搜索并确认证券
  → 选择研究意图或填写自然语言问题
  → 校验任务是否可启动
  → 创建 Research Agent Run
  → SSE/历史事件投影运行状态
  → 报告通过最终门禁并原子发布
  → 查看报告、证据和轨迹
  → 按需导出 PDF / Word / Markdown
```

字段语义调整：

- `subjectQuery`：用户输入证券代码或名称，只用于搜索和候选提示。
- `ticker`：必填，用户从解析结果中确认的唯一 A 股或 ETF 代码，创建任务时只提交规范化代码。
- `companyName`：由后端解析并只读展示，不要求用户重复填写。
- `researchIntent`：可选的研究意图，如综合研究、财务质量、估值风险、ETF 跟踪或事件影响；它为 Planner 提供目标提示，不直接决定工具链。
- `researchQuestion`：必填，决定 Planner 的研究目标和工具选择。
- `timeHorizon`、`asOfDate`、`researchDepth`、`searchMode`：保留为高级研究范围。
- `comparisonTickers`：后续 P1 能力，只有完成多证券数据、证据和报告模型后才开放。
- `AI Text`：不增加为用户开关。FinSight 的 Agent 报告本身就包含 LLM 叙述与 Java 确定性事实，关闭它会破坏报告语义。
- `PDF Report`：不增加为任务启动开关。报告完成后再调用既有导出接口生成 PDF、Word 或 Markdown。

边界：用户选择研究目标和范围，Planner 决定工具与动作；不要通过大量功能按钮把 Agent 重新改造成手动工作流。

## Step 2：重构 Research Launcher

从 `frontend/src/views/ResearchWorkspace.vue` 拆出以下组件：

- `components/research/ResearchLauncherSidebar.vue`：研究任务启动器容器。
- `components/research/ResearchReadinessStepper.vue`：展示输入准备状态。
- `components/research/SecuritySubjectPreview.vue`：展示证券解析结果。
- `components/research/ResearchScopeOptions.vue`：高级研究范围。
- `components/research/ResearchSubmitBar.vue`：状态提示和启动按钮。

建议布局：

```text
Research Launcher
├── 准备状态
├── 证券代码或名称搜索
├── 证券候选与确认结果
├── 研究意图
├── 建议问题
├── 研究问题
├── 高级研究范围（默认折叠）
│   ├── 截止日期
│   ├── 时间范围
│   ├── 研究深度
│   ├── 证据范围
│   └── 可比证券（P1）
└── 状态原因 + 启动按钮
```

调整当前左栏内容：

- 保留任务配置和启动入口。
- 将 `StatusFlow` 移到右侧 Mission Control。
- 将证券报告质检、指标、Provider 状态、Bad Case 和运行日志移到运行检查器。
- PDF 上传作为“证据范围”的附属能力，默认折叠；只有选择文档或混合检索时展开。
- 启动按钮在桌面端保持左栏底部可见，移动端使用底部操作条。

## Step 3：建立输入准备状态机

`ResearchReadinessStepper` 只表达“任务配置是否完整”，不能冒充 Agent 执行进度。

建议状态：

1. `WAITING_SUBJECT`：等待证券代码或名称。
2. `RESOLVING_SUBJECT`：正在识别证券。
3. `SELECTING_SUBJECT`：名称存在歧义，等待用户确认唯一证券。
4. `WAITING_QUESTION`：证券有效，等待研究问题。
5. `WAITING_DOCUMENT`：选择文档检索但上传尚未完成。
6. `READY`：可以创建任务。
7. `SUBMITTING`：正在创建任务，防止重复提交。

启动按钮上方必须显示明确原因：

- “请输入证券代码或名称”。
- “找到多个同名或相似证券，请先确认”。
- “未识别到受支持的 A 股或 ETF”。
- “请输入研究问题”。
- “文档正在解析，请稍候”。
- “研究任务已就绪”。

前端新增纯函数 `resolveResearchReadiness(formState)`，集中返回 `status`、`message` 和 `canSubmit`，不要在多个组件分别编写禁用条件。

## Step 4：增加证券搜索与预解析接口

基于现有 `component.analysis.StockCodeResolver` 增加只读搜索和预览入口，不创建 Agent 任务，也不修改 AgentState。代码输入可直接解析；名称输入必须返回候选项，由用户确认后才能进入 `READY`。

建议新增：

- `controller.SecurityQueryController`
- `service.SecurityQueryService`
- `service.impl.SecurityQueryServiceImpl`
- `dto.stock.SecurityCandidateResponse`
- `dto.stock.SecurityPreviewResponse`

接口：

```http
GET /api/securities/search?query=贵州茅台
GET /api/securities/{ticker}/preview
```

搜索结果至少包含规范化代码、证券名称、交易所、资产类型和匹配类型；默认最多返回 10 条，不允许前端把名称文本直接当成 `ticker` 提交。

响应至少包含：

```json
{
  "ticker": "600519",
  "fullCode": "600519.SH",
  "companyName": "贵州茅台",
  "industry": "白酒",
  "assetType": "EQUITY",
  "resolved": true
}
```

控制规则：

- 输入达到最小长度后触发，前端防抖 300～500ms。
- 新输入到达时取消或忽略旧请求结果，避免慢响应覆盖新证券。
- 只返回当前系统支持的 A 股和 ETF；名称歧义必须由用户选择，不自动猜测。
- 无法确认名称时明确返回 `resolved=false`，不能显示伪造公司名称。
- 正式 Agent Run 仍需在 `ResolveSecurityTool` 内再次解析，预览结果不能作为权威金融证据。

## Step 5：增加研究意图模板和建议问题

参考 Factor Lab 的报告类型与补充问题设计，但不为每一种卡片写死一条执行链。首版仅增加受控输入辅助：

- `COMPREHENSIVE`：综合研究，生成财务、估值、风险和证据完整性分析。
- `FINANCIAL_QUALITY`：重点研究盈利质量、现金流、成长性和异常变化。
- `VALUATION_RISK`：重点研究估值口径、风险因素和不确定性。
- `ETF_TRACKING`：仅对 ETF 显示，关注跟踪标的、规模、费率和跟踪风险。
- `EVENT_IMPACT`：研究最新公告或事件影响，强制遵守 `asOfDate` 并重新取证。

实现规则：

- 在 `ResearchRunRequest` 增加枚举型 `researchIntent`，服务端校验资产类型与意图是否匹配。
- 意图只参与 Planner 输入、默认问题和证据需求，不在 Runtime 中增加按意图硬编码的固定工具顺序。
- 前端根据已确认证券和资产类型展示 3～5 个建议问题，点击后填入或追加到 `researchQuestion`。
- 建议问题必须使用“研究、比较、解释、风险”等中性措辞，不能出现“买入、卖出、仓位、目标收益”。
- 用户填写的持仓背景只能作为时间范围和关注点上下文，不允许改变合规门禁或生成个性化交易建议。
- `quick/standard/deep` 继续表示资源预算；界面预计耗时必须来源于真实历史 telemetry，没有样本时只展示研究深度，不写固定分钟数。

## Step 6：规范可比证券能力

FinRobot 的 `Comparables` 表示同行或可比公司代码，主要用于估值比较。FinSight 暂时不要只复制一个输入框；必须等后端具备真实多证券研究能力后再开放。

P1 改造内容：

- 在 `ResearchRunRequest` 增加类型化 `comparisonTickers`，最多 3 个。
- 校验去重、排除主证券、统一交易所后缀和资产类型。
- 将对比范围写入 `ToolResearchRequest`、Planner 输入和 request context hash。
- 增加对比证券只读采集工具，分别生成独立证据与快照标识。
- 报告引用必须标明证据所属证券，避免主证券和可比证券数据串用。
- Java 使用确定性口径计算 PE/PB、增长率或其他可比较指标，LLM 只负责解释差异。
- 若任一对比证券缺数据，报告必须标记 `DATA_MISSING`，不能静默忽略。

v1 未完成以上能力前，不在界面展示 `Comparables`。

## Step 7：统一在线报告和导出链路

删除“启动任务前选择 AI Text/PDF”的产品概念，改为：

```text
Agent Run
  → 生成并审查唯一在线报告
  → Durable 完成事务保存报告版本
  → 用户在报告页选择导出格式
```

具体调整：

- 在线报告始终包含确定性指标、证据引用、LLM 叙述和免责声明。
- 继续复用 `GET /api/reports/{reportId}/export?format=pdf|docx|md`。
- 在 `ReportResearchPage.vue` 增加统一的“导出”菜单；报告库保留快捷导出。
- 导出失败不改变已经 PASS 的报告和任务状态，只提示本次导出失败。
- 所有导出格式使用相同 `reportId/version` 内容，不重新调用 LLM。
- PDF、Word、Markdown 文件名继续带 thread 和报告版本，保证可追溯。

## Step 8：建立真实 Mission Control

新增 `components/research/ResearchMissionControl.vue`，只消费 `useAgentRunProjection` 产生的权威 view state。

运行状态直接来自 canonical Agent Event：

- `run_created`：任务、预算和租约已经建立。
- `plan_created`：Planner 已生成研究计划。
- `tool_started/tool_completed`：正在执行或完成工具调用。
- `replanned`：观察或门禁问题触发重新规划。
- `synthesis_started`：开始综合报告。
- `review_completed`：完成引用、合规和质量门禁。
- `run_completed/run_stopped`：报告发布或受控停止。

禁止实现：

- 不按日志关键词映射 10%、35%、50%、75%。
- 不新增每秒轮询 `/status` 作为主状态链路。
- 不让组件自行解释同一个事件并各自保存一套状态。

Mission Control 展示：

- 当前任务和证券摘要。
- 当前 Planner 目标或动作摘要。
- 最近一次工具调用及其状态。
- 当前证据数量和有效数量。
- Replan/补证据次数。
- 最终门禁状态或停止原因。
- 当前 `QUEUED/RUNNING` 任务和最近完成报告，支持按证券、报告编号或标题搜索。
- 只有后端能够计算真实队列位置和预计等待时间时才展示这两个字段，不能根据页面任务数量猜测。

如果需要进度表达，使用“阶段状态 + 已完成项”，不展示无法准确计算的百分比。

## Step 9：拆分报告区、运行检查器和报告卡片

将当前 `ResearchWorkspace.vue` 右侧拆为：

- `ResearchReportPanel.vue`：空状态、生成中状态和报告正文。
- `ResearchRunInspector.vue`：运行详情容器。
- `AgentTracePanel.vue`：Turn/Tool/Replan 时间线。
- `EvidenceInspectorPanel.vue`：证据、来源和冲突仲裁。
- `QualityGatePanel.vue`：引用、合规、评测和停止原因。
- `RuntimeLogPanel.vue`：SSE/历史日志，只作为诊断视图。

检查器使用 Tab 或抽屉组织，默认展示报告，不让日志和调试数据抢占研究正文空间。

报告卡片和报告详情增加可复盘信息：

- 证券名称、规范化代码、报告编号、报告版本和数据截止日期。
- 一句话研究结论，但必须与正式报告内容同源，不能二次调用 LLM 临时生成。
- 引用门禁、合规门禁、评测结果、有效证据数量和风险等级。
- 研究问题、研究意图、研究深度、搜索模式、使用的 Planner/Tool 版本。
- Snapshot/Checkpoint/Context Hash 等技术字段放在“研究配置快照”抽屉，不干扰普通用户阅读。
- 阅读和导出直接复用既有报告版本；公开分享在权限、脱敏和合规机制完成前不开放。

空状态参考 FinRobot 的主区域，但使用 FinSight 业务内容：

- 展示“财务表现、估值观察、风险与证据审查”三类能力。
- 提供 2～3 个可直接填入的示例研究问题。
- “开始新研究”只聚焦证券代码输入，不额外创建第二套启动入口。

## Step 10：优化任务提交、断线恢复和重复点击

提交规则：

- 点击后立即在前端建立 `SUBMITTING` 状态，冻结本次请求快照。
- 后端返回 `taskId` 后，以真实任务替换本地提交状态并绑定 SSE。
- 创建请求失败时恢复表单，保留用户输入并显示可操作错误。
- 同一个提交动作使用客户端幂等键；重复点击不能创建两个相同任务。
- 任务创建成功后即使 SSE 首次连接失败，也通过事件回放接口加载已提交事件。
- 页面刷新后根据持久化 task/thread 重新订阅，不依赖浏览器内存任务对象。

继续复用现有：

- Agent Event Outbox。
- `Last-Event-ID/afterSequence` 续传。
- `useAgentRunProjection` 实时与历史共用 reducer。
- Durable Turn 和最终报告原子提交。

## Step 11：先实现“基于报告继续研究”，再建立多会话

Factor Lab 证明金融投研产品不必先做完整 Chat。FinSight 先在报告页增加“继续研究”入口，以较低复杂度获得解释、更新和比较能力：

```text
已完成报告
  → 用户选择继续研究动作
  → Report Context Builder 提取受控上下文
  → 用户确认或修改新问题
  → 创建新的独立 Agent Run
  → 新报告记录 sourceReportId
```

首版支持三类动作：

- “解释这个结论”：携带被选中的报告段落、引用 ID 和报告版本，新 Run 仍执行引用校验。
- “更新到最新数据”：只携带研究范围和旧结论，强制重新采集事实，不能复用旧快照冒充最新数据。
- “与另一证券比较”：要求用户确认对比证券，只有 Step 6 的多证券模型完成后开放。

新增 `ReportContextBuilder` 只输出结构化 `PreviousResearchContext`，至少包含 `sourceReportId`、`reportVersion`、`ticker`、`asOfDate`、`selectedClaim`、`citationIds` 和 `unresolvedIssues`。禁止把整份报告和全部 Agent Trace 无限制追加到 Planner Prompt。

每次继续研究仍创建新的 `taskId`、AgentState、预算、Checkpoint、Tool Journal 和报告版本；通过 `sourceReportId` 建立溯源关系，不复用上一次 Run 的可变状态。

完成该阶段后，再将当前页面临时 `SESSION_THREAD_ID` 替换为后端创建的持久 Research Session。

建议结构：

```text
Research Session
├── 用户消息 1
├── Agent Run 1 / 报告 V1
├── 用户追问 2
├── Agent Run 2 / 回答或报告 V2
└── 会话摘要、当前研究范围、未解决问题
```

关键规则：

- 一个 Session 可以有多条消息和多个 Agent Run。
- 每个 Agent Run 保留独立 AgentState、预算、Checkpoint 和 Tool Journal。
- Conversation Memory 只保存消息、会话摘要和研究范围。
- Financial Knowledge 继续保存证据、快照和报告版本。
- 不把完整聊天记录直接写入 Planner；使用最近消息和结构化摘要生成独立 Research Brief。
- “现在、最新、是否仍成立”等追问强制重新取证。
- “解释报告中的某个结论”可复用冻结报告和原证据，但仍要保留引用校验。

未来多会话布局：

```text
左侧：Research Session 列表
中间：对话与报告
右侧抽屉：任务配置、Agent 轨迹、证据和门禁
```

因此本轮 Research Launcher 要做成可复用组件或抽屉，不要永久硬编码为占据全局左栏的唯一内容。

## Step 12：测试与验收

### 前端测试

- `resolveResearchReadiness` 覆盖缺证券、解析中、缺问题、缺文档、就绪和提交中。
- 证券预解析覆盖快速连续输入、旧响应晚到和无效代码。
- 证券名称搜索覆盖多候选、手动确认、资产类型过滤和名称文本不能直接提交。
- 研究意图只改变 Planner 上下文和问题建议，不在前端写死工具执行顺序。
- 启动按钮重复点击只产生一次请求。
- Agent Event reducer 覆盖重复事件、乱序事件、Replan、停止、断线续传和历史回放。
- 报告导出失败不改变报告 PASS 状态。
- 桌面宽度下 Launcher 固定可见；移动端使用抽屉或纵向布局，无横向溢出。

### 后端测试

- `SecurityQueryController` 和 `SecurityQueryService` 覆盖股票、ETF、带后缀代码和非法代码。
- 证券搜索覆盖代码、名称、同名/相似候选、结果上限和不受支持资产过滤。
- 正式运行仍通过 `ResolveSecurityTool` 重新解析，不信任客户端预览内容。
- `ReportContextBuilder` 只携带允许的报告上下文；更新到最新数据时必须重新取证。
- 基于报告继续研究会创建新 Agent Run，旧 Run 的 AgentState、Checkpoint 和预算不发生变化。
- 若实现 `comparisonTickers`，覆盖去重、上限、主证券排除、证据归属和缺失降级。
- 导出 PDF、Word、Markdown 均使用同一报告版本，导出过程不调用 LLM。
- 任务创建幂等键、SSE 重连、事件回放与既有 outbox 契约通过回归。

### 端到端验收场景

1. 输入 `600519`，自动显示 `600519.SH / 贵州茅台 / 普通股票`。
2. 输入“贵州茅台”时展示候选证券，确认后才能提交规范化代码。
3. 选择“财务质量”后出现相应建议问题，但 Planner 仍可自主选择白名单工具。
4. 未输入研究问题时不能启动，并显示明确原因。
5. 启动后立即进入提交状态，获得 taskId 后展示真实 Planner/Tool/Guard 事件。
6. 运行中断开 SSE，再连接后从缺失 sequence 继续，页面结果与完整 Trace 一致。
7. PASS 后在线报告可查看，并能分别导出 PDF、Word、Markdown。
8. 报告详情展示研究配置快照、数据截止日、证据数量和质量门禁结果。
9. 从报告发起“更新到最新数据”后创建新 taskId，新报告可追溯 sourceReportId 且事实重新采集。
10. PDF 导出失败时在线报告、报告版本和任务完成状态保持不变。
11. 若任务受控停止，页面展示明确 stop reason，不伪装成完成报告。

## 暂时不要做

- 不照搬 FinRobot 的 FastAPI、单 HTML、Vue CDN 或 Tailwind CDN 技术实现。
- 不使用进程内 `tasks = {}` 作为任务权威状态。
- 不使用日志关键词估算 Agent 百分比。
- 不为“看起来功能丰富”增加没有后端语义的 Comparables、Sensitivity、News+、Charts+ 开关。
- 不允许用户关闭关键报告叙述、引用审查或合规门禁。
- 不在创建任务前生成 PDF；导出是报告发布后的独立动作。
- 不把完整对话历史直接追加到每轮 Planner Prompt。
- 不复用上一个 Agent Run 的 AgentState 处理下一条用户追问。
- 不把 Factor Lab 的“补充问题”误称为多轮会话，也不因竞品没有 Chat 就取消 Session 的后续演进。
- 不照搬积分系统、圆桌角色数量、固定耗时承诺或“量价决策”表述。
- 不在完成权限、脱敏与合规机制前开放用户报告公开分享。
